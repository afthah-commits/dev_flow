# Phase 46 Verification Report — Production Database & Migration Reliability

## 1. Root cause

Migration `d36b2909d14d` ("Phase 32 release models") was autogenerated against a dev database that still contained `_alembic_tmp_attachments` — a leftover Alembic **batch-operation temp table** (SQLite batch mode copies a table to `_alembic_tmp_<name>`, then drops it). Alembic captured that artifact into the migration diff:

- `upgrade()`: unconditional `op.drop_table('_alembic_tmp_attachments')` — on a fresh DB the table never existed, so `alembic upgrade head` failed with `sqlite3.OperationalError: no such table: _alembic_tmp_attachments`.
- `downgrade()`: unconditional `op.create_table('_alembic_tmp_attachments', ...)` — recreated the artifact instead of restoring the real schema.

Reproduced exactly on a fresh temp SQLite DB before fixing. The real `attachments` table is created by `20c726902fae` and is unrelated to the temp artifact. Precedent for this exact class of bug already existed in `f24f953c5076` (Phase 17), which had fixed the same artifact with a `has_table` guard and a comment.

## 2. Fix

Minimal, pattern-consistent change in [d36b2909d14d_phase_32_release_models.py](backend/alembic/versions/d36b2909d14d_phase_32_release_models.py) only:

- Upgrade: replaced the unconditional drop with `if sa.inspect(op.get_bind()).has_table('_alembic_tmp_attachments'): op.drop_table(...)` plus an explanatory comment. Existing dev DBs that still carry the artifact are cleaned up as before; fresh DBs skip it.
- Downgrade: removed the `op.create_table('_alembic_tmp_attachments', ...)` block, replaced with the same NOTE comment style used in `f24f953c5076` (downgrade must not recreate a batch-mode artifact).

No other migrations touched, no history rewritten, no error suppression.

## 3. Fresh DB verification

Temporary empty SQLite DB (`tmp_fresh46.db`, deleted after verification) via `alembic upgrade head`:

- Before fix: `OperationalError: no such table: _alembic_tmp_attachments` (captured).

Existing dev DB (`devflow.db`): already at head; `alembic upgrade head` is a clean no-op and stays at `b2c3d4e5f6a7`.
